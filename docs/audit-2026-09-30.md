# Whole-app audit — optimization and enhancement (2026-09-30)

Read-only audit of NuvioDesktop (upstream `Dev` @ `fe92d414` + the refresh-rate fork), Windows target. Four parallel
reviews (playback/native, UI, data/network/security, build/packaging/tests); the top claims were re-checked in the code
by hand. **C** = confirmed in code (traced), **P** = plausible (not traced end to end or not measured).
Effort: S < ½ day, M 1–3 days, L more. "Where" = file:line under `composeApp/src/` unless a path says otherwise.

Most findings are **upstream code**. Fixing them in the fork grows the upstream diff beyond the 12/3/6 hook budget
(Q42/Q44), so each fix is either an upstream PR (the feature request is on hold, Q3) or a budget decision.

## Tier 1 — small fixes, real risk or clear gain

| # | Finding | Where | Why it matters | Effort |
|---|---|---|---|---|
| 1 | **Preference writes are not atomic; a broken file is silently wiped.** `persist()` truncates and rewrites in place; a failed load is ignored. (C) | `desktopMain/.../core/storage/DesktopStorage.kt:151-168` | A crash/power loss mid-write empties watch progress, Trakt/debrid tokens, addons; the next write makes the loss permanent. Fix: temp file + `ATOMIC_MOVE` (as `DesktopCache` already does) + `.bak` fallback. | S |
| 2 | **A download rewrites its whole prefs file and recomposes the app shell every 8 KB.** (C) | `DownloadsPlatformDownloader.desktop.kt:85-92` → `DownloadsRepository.kt:307-318, 370-383, 407-410`; `MainAppContent.kt:334-337` | Thousands of file rewrites + shell recompositions per second at 100 Mbit/s; the unlocked read-modify-write can undo a Pause. Fix: progress ≤ 4 Hz, persist on status change only. | S |
| 3 | **Window geometry saved on every move/resize event, 4 file rewrites each, on the UI thread.** (C) | `desktopMain/.../Main.kt:170-190`, `DesktopWindowModeStorage.kt:51-56` | Jank while dragging, and it multiplies #1's risk. Fix: `debounce(500)` + IO dispatcher. | S |
| 4 | **Playback errors after `loadfile` never reach Kotlin: a dead stream spins forever.** The bridge's event loop only handles `SHUTDOWN`; no `END_FILE`/error path. (C) | `native/windows/player_bridge.cpp:1890-1908` | A 403/404/expired debrid link shows an endless spinner; the credential-refresh fallback (`PlayerScreenRuntimeEffects.kt:763`) can't fire on desktop. | S–M |
| 5 | **Adding an addon subtitle can freeze the UI:** `sub-add <url>` runs synchronously under `mpvMutex`, called from the EDT; mpv downloads the file inside the call. (C) | `NativePlayerController.kt:1014-1020` → `player_bridge.cpp:1154-1157, 1999-2010` | 0.2–2 s freezes of the UI and the controls overlay (P for the length). Fix: `mpv_command_async` / off the EDT. | S |
| 6 | **Old native runtime copies are never deleted.** Each build adds a 113 MB folder. (C, measured: 3 × 113 MB = 337 MB in the official profile) | `desktopMain/.../core/storage/DesktopCache.kt:9-21` | Disk grows ~113 MB per app update (also `player-ui`, `quickjs`). Fix: delete sibling versions after install. | S |
| 7 | **QuickJS scrapers run on a multi-threaded pool; the "flaky" test is probably a real race.** Desktop uses `Dispatchers.Default`; iOS limits parallelism; no evaluation timeout on desktop (Android has one). (P for the race, C for the config) | `desktopMain/.../plugins/runtime/PluginRuntime.desktop.kt:7-9`, `fullCommonMain/.../js/JsRuntime.kt:14-18` | Explains the known-failure `PluginRuntimeDesktopTest` NPE (`this.closed` = use after close); a `while(true)` scraper holds a thread + permit forever. Fix: one confined thread per runtime + Android's timeout. | S–M |
| 8 | **Executables/DLLs are loaded from paths relative to the working directory before the bundled ones.** (C) | `NativePlayerBridge.kt:221-228`, `P2pStreamingEngine.desktop.kt:487-496` | Starting the app from a folder someone controls runs their `player_bridge.dll`/TorrServer. Also observed: the fork's packaged test runs (started from the repo) loaded the repo's build DLL this way. Fix: dev paths only behind a dev system property. | S |
| 9 | **Fork: the NVIDIA driver read and mode enumeration run while mpv waits at the hook, on every start** (also "already at target", i.e. most titles at 240 Hz). (C, measured 150–160 ms) | `native/windows/display_mode_matcher.cpp:1240-1242`, `RefreshRateController.kt:152-173` | ~0.15–0.2 s later first frame with the feature on. Fix: start the read at H2 on a worker / cache per process. **Fork-owned, no hook budget.** | S |

2. **Data safety, tiny diffs:** #1, #2, #3, #6 — best as upstream PRs; in the fork they need ~10–25 more upstream
   lines (a new budget decision).
3. **Playback correctness:** #4, #5, R1, #17 — upstream `player_bridge.cpp` (the fork's hot spot; conflicts to expect).
4. **Performance:** #10, #11–#14, #15–#16, #21–#22.
